协同文档编辑记录与版本回溯系统

摘要

随着远程办公需求增长，实时协同编辑系统已成为现代办公的基础工具。传统方案基于操作转换（OT）算法，依赖中央服务器解决冲突，存在单点故障风险高、离线支持差等问题。无冲突复制数据类型（CRDT）作为新兴分布式算法，无需中央协调即可实现多节点数据的自动合并与一致性保障。

本文设计并实现了基于CRDT的实时协同文档编辑系统。系统采用前后端分离架构，前端基于Next.js构建单页应用，后端基于NestJS提供RESTful API，通过WebSocket与Hocuspocus服务器实现实时同步。核心层采用Yjs库实现CRDT算法，基于YATA算法为操作分配唯一标识，确保并发编辑的自动合并与冲突消解。版本管理支持自动快照、手动保存和版本回溯，并提供HTML差异对比可视化。数据层采用PostgreSQL存储元数据，以二进制形式持久化Yjs状态，通过Redis实现缓存与跨实例同步。

系统实现了用户认证、文档管理、实时协同编辑、版本回溯和权限管理等核心功能，采用HttpOnly Cookie保障认证安全，基于角色的访问控制实现细粒度权限管理，支持通过Redis Pub/Sub进行水平扩展，满足中小型团队协同办公需求。

关键词：协同编辑；CRDT；Yjs；实时同步；版本管理

Collaborative Document Editing with Version Control

Abstract

With the growing demand for remote work, real-time collaborative editing systems have become essential tools for modern office environments. Traditional solutions rely on the Operational Transformation (OT) algorithm, which depends on a central server for conflict resolution, introducing risks such as single points of failure and poor offline support. Conflict-free Replicated Data Types (CRDT), an emerging distributed algorithm, can achieve automatic data merging and consistency across multiple nodes without requiring a central coordinator.

This paper designs and implements a real-time collaborative document editing system based on CRDT. The system adopts a separated front-end and back-end architecture: the front-end is built as a single-page application using Next.js, while the back-end provides RESTful API services using NestJS, achieving real-time synchronization via WebSocket and a Hocuspocus server. At the core layer, the Yjs library implements the CRDT algorithm, assigning unique identifiers to each operation based on the YATA algorithm to ensure automatic merging and conflict resolution of concurrent edits. Version management supports automatic snapshots, manual saves, and version rollback, along with HTML-based diff visualization. The data layer uses PostgreSQL for metadata storage, persists Yjs states in binary format, and leverages Redis for caching and cross-instance synchronization.

The system implements core features including user authentication, document management, real-time collaborative editing, version rollback, and permission management. HttpOnly Cookies ensure authentication security, role-based access control provides fine-grained permission management, and horizontal scaling is supported through Redis Pub/Sub, meeting the collaborative needs of small to medium-sized teams.

Keywords: Collaborative Editing; CRDT; Yjs; Real-time Synchronization; Version Management

1绪论

1.1研究背景与意义

进入二十一世纪以来，互联网技术的飞速发展深刻改变了人类社会的生产与协作方式。特别是近年来，随着云计算、大数据和移动互联网技术的成熟普及，远程办公和在线协作逐渐从特殊时期的应急手段转变为常态化的工作模式。根据全球知名咨询机构Gartner的调查报告，截至2025年，全球约有超过70%的知识工作者采用了某种形式的远程或混合办公模式。在这一趋势下，实时协同文档编辑系统作为支撑分布式团队高效协作的核心工具，其重要性日益凸显。

协同文档编辑是指多个用户通过网络同时对同一份文档进行编辑操作，并且能够实时看到其他用户的编辑内容和光标位置。这一技术的核心挑战在于如何高效地处理多用户并发编辑时产生的冲突。在传统的单用户文档编辑场景中，编辑操作的执行顺序是确定的，不存在冲突问题。然而在多用户协同编辑场景下，不同用户可能在同一时刻对文档的同一位置进行修改，如何确保所有用户最终看到的文档内容一致，是协同编辑技术需要解决的核心问题。

在协同编辑领域，目前主要存在两种冲突解决技术路线：操作转换（Operational Transformation，OT）和无冲突复制数据类型（Conflict-free Replicated Data Types，CRDT）。OT算法由Ellis和Gibbs于1989年首次提出，其核心思想是在检测到并发操作时，通过转换操作参数来保证操作执行结果的一致性。Google Docs是目前最广为人知的基于OT算法的协同编辑产品，其成功证明了OT算法在实际应用中的可行性。然而，OT算法存在一个根本性的局限：它依赖中央服务器作为操作排序的唯一仲裁者，所有的操作转换都需要在服务器端完成。这种架构导致了几个问题：首先，服务器成为系统的单点故障节点，一旦服务器宕机，整个协同编辑功能将不可用；其次，OT算法的实现复杂度较高，操作转换函数的正确性验证困难；最后，OT算法难以支持真正的离线编辑，因为离线期间产生的操作无法在服务器端进行转换。

CRDT作为一种新兴的分布式协同算法，为解决上述问题提供了全新的思路。CRDT的核心思想是设计一类特殊的数据结构，使得无论操作以何种顺序到达各节点，只要所有操作最终都被传递到所有节点，各节点的状态最终会收敛到一致。CRDT的这一特性使其天然支持离线编辑和去中心化架构。在文本协同编辑场景中，基于CRDT的Yjs库通过YATA（Yet Another Transformation Approach）算法，为文档中的每个字符或元素分配包含客户端标识符和逻辑时钟的唯一标识，通过确定性的排序规则解决并发插入的冲突问题。

在此背景下，本文以设计和实现一个基于CRDT的实时协同文档编辑系统为研究目标，旨在探索CRDT技术在Web环境下的协同编辑应用实践。本系统采用Yjs作为CRDT的实现库，基于Hocuspocus服务器实现WebSocket实时通信，结合Next.js前端框架和NestJS后端框架构建完整的协同编辑解决方案。本研究的意义主要体现在以下几个方面：

第一，技术探索意义。通过实际系统的设计与实现，深入验证CRDT技术在Web协同编辑场景中的可行性和优势，为相关技术的工程实践提供参考。与传统的OT方案相比，本系统展示了CRDT在离线编辑支持、去中心化架构和实现复杂度方面的改进。

第二，应用实践意义。本系统实现了包含用户认证、文档管理、实时协同编辑、版本管理等完整功能的协同编辑平台，为中小型团队的远程协作提供了可用的工具支持。系统的开源技术栈和模块化设计使得其具有良好的可扩展性和可定制性。

第三，学术研究意义。本文对CRDT算法在协同编辑中的应用进行了系统性的分析和总结，对版本管理机制的设计进行了深入探讨，为后续的相关研究工作提供了基础。

1.2国内外研究现状

协同文本编辑在国内外都有极高的热度，国内外学者从许多角度进行了大量研究。本节将从国内研究和国外研究两个方面对现有研究成果进行综述。

1.2.1国内研究现状

国内在协同编辑领域的研究起步相对较晚，但近年来随着国产办公软件的崛起和远程办公需求的增长，相关研究呈现出加速发展的态势。

在学术研究层面，国内高校和科研机构在协同编辑算法方面取得了一系列成果。周义盼[1]针对基于WebSocket的协同编辑系统进行了设计与实现研究，提出了基于WebSocket长连接的实时数据推送方案，解决了HTTP短轮询模式下的延迟和带宽浪费问题，为Web环境下的协同编辑通信架构提供了参考。何发智等人[2]对支持操作意图一致性的实时协同编辑算法进行了系统综述，梳理了OT算法的发展脉络和关键改进方向，提出了操作意图一致性的形式化定义框架。卢暾和顾宁[3]对实时协同中的一致性维护关键技术进行了深入研究，分析了收敛性、因果序保持和意图保持三个一致性模型的理论基础和实现方法。王名悠和王晓斌[4]针对实时协同文本编辑系统中共享文档的一致性维护问题，提出了基于操作转换的一致性维护算法，在保证操作收敛性的同时优化了转换函数的执行效率。王名悠[5]在其学位论文中设计并实现了一个分布式实时协同文本编辑系统，对系统的并发控制机制和通信架构进行了完整的工程实践。苗星[6]在WebRTC系统中设计并实现了协同编辑子系统，探索了基于P2P通信架构的协同编辑方案，对比了P2P模式与中心化服务器模式在延迟和可靠性方面的差异。朱鸣[7]对协同图形编辑系统中的并发控制问题进行了研究，将OT算法从文本协同扩展到图形协同领域，解决了图形操作（移动、缩放、旋转）的冲突解决难题。

在产业应用层面，国内的协同编辑产品发展迅速。字节跳动旗下的飞书文档（原Lark Docs）是国内协同办公领域的代表性产品，其协同编辑引擎基于OT算法实现，通过自研的高性能协同服务器支撑了大规模并发编辑场景。阿里巴巴的钉钉文档和腾讯的腾讯文档也分别基于OT算法实现了协同编辑功能，并在各自的生态系统中得到了广泛应用。金山办公的WPS云文档作为国内办公软件的先行者，在传统本地编辑的基础上逐步引入了协同编辑能力，其协同引擎经历了从OT到混合架构的演进过程。石墨文档作为国内早期的协同文档产品，在协同编辑的用户体验设计方面积累了丰富的经验。

然而，国内现有的协同编辑产品在技术架构上仍以OT算法为主流方案，对CRDT技术的应用和探索相对较少。这主要源于OT算法经过多年发展已具备成熟的工程实践方案，而CRDT在Web环境下的工程化应用仍处于发展阶段。但随着WebAssembly等技术的成熟和CRDT理论研究的深入，基于CRDT的协同编辑方案在国内正受到越来越多的关注。

1.2.2国外研究现状

国外在协同编辑领域的研究历史悠久，成果丰富，涵盖了从基础理论到工程实践的各个方面。

在基础理论层面，CRDT的概念由Marc Shapiro等人[8]在2011年正式提出，其论文《Conflict-free Replicated Data Types》系统性地阐述了CRDT的理论基础和分类体系，为后续研究奠定了坚实的理论基础。在此之后，CRDT的研究沿着两个主要方向展开：基于状态的CRDT（State-based CRDT，也称CvRDT）和基于操作的CRDT（Operation-based CRDT，也称CmRDT）。在文本编辑这一特定应用场景中，Kleppmann等人[9]对CRDT在协同文本编辑中的应用进行了深入研究，提出了支持JSON嵌套数据结构的CRDT实现方案，并对现有CRDT算法的正确性和性能进行了系统的形式化分析和对比。Litt等人[10]于2022年提出了Peritext算法，将CRDT从纯文本场景扩展到富文本编辑领域，支持段落级别的格式化操作协同，解决了此前CRDT方案仅适用于纯文本的局限。

在算法实现层面，CRDT文本协同编辑算法经历了从早期探索到工程优化的演进过程。Ellis和Gibbs[11]于1989年首次提出了操作转换的概念，为后续的协同编辑算法研究奠定了基础。Sun等人[12]于1998年对实时协同编辑系统的一致性模型进行了形式化定义，提出了收敛性（Convergence）、因果序保持（Causality Preservation）和意图保持（Intention Preservation）三个核心一致性条件，为协同编辑算法的正确性验证提供了理论框架。在此之后，一系列CRDT文本算法被相继提出：WOOT（WithOut Operational Transform）算法于2005年提出，通过为每个字符分配全局唯一标识符实现去中心化的冲突解决，但其空间复杂度较高；Treedoc算法于2009年由Preguiça等人[13]提出，采用二叉树结构组织文档中的字符位置，通过路径编码实现确定性排序；Logoot-Undo算法由Weiss等人[14]于2010年提出，在Logoot算法的基础上增加了撤销操作的支持，解决了CRDT场景下操作的语义撤销问题；RGA（Replicated Growable Array）算法由Roh等人[15]于2011年提出，通过时间戳和操作依赖关系实现高效的并发插入排序。Yjs是目前最成熟的开源CRDT实现之一，由Kevin Jahns开发维护。Yjs基于YATA算法，该算法在上述工作的基础上进行了深度优化。YATA算法的核心创新在于为每个插入操作分配一个包含客户端ID和逻辑时钟的唯一标识符，并通过确定性的排序规则解决并发冲突。与早期的CRDT文本算法相比，YATA算法在时间和空间复杂度上均有显著优化。Automerge是另一个重要的CRDT实现，由Martin Kleppmann主导开发，其设计理念更偏向于通用数据结构的CRDT实现，支持JSON-like的嵌套数据结构。

在产品应用层面，国外的协同编辑产品丰富多样。Google Docs作为协同文档编辑的标杆产品，其协同引擎基于OT算法实现，经过十余年的迭代优化，已经支撑了全球数亿用户的日常协同编辑需求。Notion作为新一代协作工具的代表，将协同编辑与知识管理、项目管理等功能深度整合，其底层采用了混合协同引擎架构。Figma作为设计领域的协同工具，在图形协同编辑方面做出了开创性的工作，其协同引擎基于CRDT的变体实现。VS Code的Live Share功能提供了代码级别的协同编辑能力，基于OT算法实现了低延迟的代码同步。 cider和Quip等新兴产品也在探索协同编辑的新范式。

在服务器基础设施层面，Hocuspocus是一个专为Yjs设计的协同编辑后端服务器，提供了文档持久化、用户认证、WebSocket连接管理等开箱即用的功能模块。Hocuspocus采用可扩展的插件架构设计，开发者可以通过自定义钩子函数灵活地集成业务逻辑。SyncedStore和Y-Sweet等开源项目则进一步降低了基于Yjs构建协同应用的门槛。

综上所述，协同编辑技术在国内外已经得到了广泛的研究和应用。OT算法作为成熟的工程方案支撑了主流协同编辑产品的运行，而CRDT作为新兴技术正在快速发展。本系统选择基于CRDT的Yjs库作为协同编辑引擎，结合Hocuspocus服务器和现代Web技术栈，旨在构建一个高性能、可扩展的实时协同文档编辑系统。

1.3研究内容

本文以基于CRDT的实时协同文档编辑系统为研究对象，主要研究内容包括以下几个方面：

（1）协同编辑算法分析与选型。深入分析OT算法和CRDT的基本原理、优缺点和适用场景，对比两者在冲突解决机制、离线编辑支持、服务器依赖性等方面的差异，论证CRDT技术在本系统中的适用性。

2.1 CRDT与Yjs协同框架

CRDT（Conflict-free Replicated Data Types，无冲突复制数据类型）是一类特殊的分布式数据结构，它允许多个节点独立地对本地副本进行修改，并保证在操作传播完成后所有副本最终收敛到相同的状态。CRDT的理论基础来源于分布式系统中的乐观复制（Optimistic Replication）[16]和最终一致性概念[17]，其核心优势在于不需要中央协调器即可实现多节点间的一致性。根据CAP定理[18]，分布式系统在一致性（Consistency）、可用性（Availability）和分区容错性（Partition tolerance）三者中最多同时满足两者。CRDT通过选择最终一致性模型，在保证可用性和分区容错性的前提下实现了多节点间的数据同步。

CRDT分为两大类别：基于状态的CRDT（CvRDT）和基于操作的CRDT（CmRDT）。基于状态的CRDT通过传输完整状态并在接收端进行合并操作来实现同步，状态的合并操作需要满足交换律、结合律和幂等性三个数学性质。基于操作的CRDT通过传播操作本身来实现同步，要求操作满足交换律和幂等性。在协同文本编辑场景中，通常采用基于操作的CRDT方案，因为文本编辑操作（如插入和删除字符）的粒度较小，传播操作比传播完整状态更加高效。

CRDT在离线编辑支持、服务器去依赖和实现复杂度方面具有明显优势，而OT算法在空间效率和成熟度方面仍有优势。对于本系统所面向的中小型团队协同编辑场景，CRDT的离线编辑支持和去中心化架构特性更为重要，因此本系统选择基于CRDT的Yjs库作为协同编辑引擎。

Yjs是目前最成熟和性能最优的CRDT文本协同编辑实现库之一，由Kevin Jahns开发并开源维护。Yjs基于YATA（Yet Another Transformation Approach）算法，该算法专门针对文本协同编辑场景进行了深度优化。YATA算法的核心思想是为文档中的每个字符或文本块分配一个全局唯一标识符，该标识符由客户端ID和逻辑时钟两部分组成。当多个用户在文档的同一位置进行并发插入时，YATA通过确定性的排序规则（先比较逻辑时钟，再比较客户端ID）来确定字符的最终位置，从而避免冲突。

Yjs的核心数据结构包括Y.Doc、Y.Text、Y.Map和Y.Array。Y.Doc是文档的根容器，管理所有共享数据类型和更新操作。Y.Text用于表示可变长度的文本内容，支持插入、删除和格式化操作，是协同文本编辑的核心数据结构。Y.Map提供了键值对映射功能，常用于存储文档的元数据信息。Y.Array提供了有序列表功能，支持在任意位置插入和删除元素。

Yjs的更新同步机制采用了状态向量（State Vector）的概念。状态向量记录了每个客户端已处理的最后逻辑时钟值，其设计灵感来源于Lamport[19]提出的逻辑时钟机制，通过比较两个状态向量可以确定两者之间的差异更新。这种增量同步机制使得Yjs只需要传输缺失的更新操作，而非完整的文档状态，显著降低了网络带宽消耗。在二进制编码方面，Yjs采用了高效的二进制编码格式，将操作数据压缩为紧凑的二进制字节序列，进一步减少了网络传输的数据量。

2.2 Next.js前端框架简介

Next.js是由Vercel公司开发维护的开源React框架，是目前最流行的React服务端渲染（Server-Side Rendering，SSR）解决方案之一。本系统采用Next.js 15版本，该版本引入了多项重要的架构改进。

Next.js 15的核心特性之一是App Router，它基于React Server Components（RSC）技术重新设计了路由和渲染架构。App Router支持三种渲染模式：服务端渲染（SSR）、静态生成（Static Site Generation，SSG）和客户端渲染（Client-Side Rendering，CSR）。服务端组件默认在服务器上执行，不包含交互逻辑和客户端JavaScript代码，有助于减少客户端的JavaScript包体积。客户端组件通过”use client”指令标记，在浏览器中执行，支持交互功能和状态管理。

在路由组织方面，App Router采用了基于文件系统的路由方案，通过文件夹结构定义路由层级。路由组（Route Groups）功能允许通过括号语法将相关路由组织在同一目录下而不影响URL路径，本系统利用这一特性将认证页面（login、register）和主应用页面分别组织在不同的路由组中。

Next.js还提供了内置的优化功能，包括自动代码分割、图片优化、字体优化等。在样式管理方面，Next.js原生支持CSS Modules、Tailwind CSS等多种方案。本系统采用Tailwind CSS作为样式解决方案，结合CSS变量实现主题系统，支持亮色和暗色两种模式切换。

App Router支持的三种渲染策略各有其适用场景，本系统根据页面特征选择了不同的渲染策略。三种渲染策略的对比如表2-1所示。

2.3 NestJS后端架构

NestJS是一个基于TypeScript的渐进式Node.js服务端框架，其设计灵感来源于Angular框架的模块化架构。NestJS采用装饰器（Decorators）和依赖注入（Dependency Injection）的设计模式，提供了高度模块化、可测试和可维护的应用开发体验。

NestJS的核心概念是模块（Module），每个模块封装了一组相关的控制器（Controller）、服务（Service）和提供者（Provider）。本系统的后端采用以下模块划分：AuthModule负责用户认证和授权，DocumentsModule负责文档管理业务，CollaborationModule负责协同编辑的核心逻辑，VersionsModule负责版本快照管理，PrismaModule负责数据库访问层。

在请求处理流程方面，NestJS采用了管道（Pipe）、守卫（Guard）、拦截器（Interceptor）和过滤器（Filter）等中间件机制。管道用于请求数据的验证和转换，本系统使用全局验证管道（ValidationPipe）结合class-validator装饰器实现请求参数的自动校验。守卫用于权限控制，本系统使用JWT认证守卫保护需要登录才能访问的接口。拦截器用于在请求处理前后执行通用逻辑，本系统使用响应转换拦截器统一API响应格式。异常过滤器用于捕获和处理异常，本系统使用全局异常过滤器返回标准化的错误响应。

NestJS还提供了WebSocket的支持，通过@WebSocketGateway装饰器可以方便地创建WebSocket网关。本系统利用这一能力与Hocuspocus服务器进行集成，实现了协同编辑的实时数据同步。

NestJS的依赖注入（Dependency Injection）是其核心设计模式之一。通过@Injectable装饰器标记的服务类会被自动注册到IoC（Inversion of Control）容器中，其他模块通过构造函数注入的方式获取服务实例。这种模式解耦了服务的创建和使用，使得单元测试时可以方便地替换为模拟对象。本系统中，AuthService注入了PrismaService和JwtModule，DocumentsService注入了PrismaService，模块间的依赖关系清晰明确。

2.4 PostgreSQL与Prisma ORM

PostgreSQL作为业界领先的开源关系型数据库管理系统，凭借其卓越的可靠性、数据完整性和强大的扩展性，成为构建企业级应用的首选数据库[20]。本系统选用PostgreSQL 17版本，该版本在性能、安全性和功能完整性方面均有显著提升，为本系统的稳定运行提供了坚实保障。PostgreSQL支持丰富的数据类型体系，特别是对二进制大对象（Binary Large Object，BLOB）类型的完善支持，这一特性对于本系统存储Yjs文档的二进制状态数据至关重要。通过使用`BYTEA`类型存储CRDT文档状态，系统实现了高效的数据持久化和快速的数据恢复。同时，PostgreSQL的MVCC（多版本并发控制）机制和先进的查询优化器，确保了在高并发场景下的数据一致性和查询性能，为协同编辑系统的实时性要求提供了技术支撑。

在数据库访问层，本系统采用Prisma这一现代化的TypeScript ORM框架。Prisma通过提供端到端的类型安全解决方案，彻底解决了传统ORM工具中常见的数据类型不一致和运行时错误问题。该框架的核心架构包含三个关键组件：Prisma Schema定义语言（DSL）允许开发者以声明式方式定义数据库模型及其复杂关系；Prisma Client作为类型安全的查询构建器，能够根据Schema自动生成优化的TypeScript代码；Prisma Migrate则提供了声明式的数据库迁移管理工具，确保数据库Schema的版本化演进过程安全可控。

本系统的数据模型设计充分考虑了协同编辑场景的特殊需求。通过Prisma Schema，我们定义了六个核心实体：用户表（User）管理系统认证和用户信息；会话表（Session）处理用户登录状态和令牌管理；文档表（Document）存储文档元数据和基础信息；文档协作者表（DocumentCollaborator）实现细粒度的权限控制；文档版本表（DocumentVersion）记录文档的历史版本信息；文档编辑记录表（DocumentEdit）跟踪每一次编辑操作的详细信息。这些实体之间通过外键约束建立严格的关系模型，确保了数据的引用完整性和一致性。

Prisma在本系统中的优势尤为突出。其声明式的Schema定义方式不仅提高了代码的可读性和可维护性，更重要的是自动生成的TypeScript类型为整个应用提供了编译时类型检查，显著减少了因类型不匹配导致的运行时错误。开发者只需维护Schema文件，Prisma即可自动生成类型安全的数据库访问代码，大幅提升了开发效率和代码质量。此外，Prisma Migrate工具通过生成版本化的迁移脚本，实现了数据库Schema变更的透明化管理，支持团队协作开发时的数据库同步和回滚操作，保障了数据库演进的可靠性和可追溯性。

2.5 WebSocket与Hocuspocus服务器

WebSocket是一种在单个TCP连接上实现全双工通信的网络协议。与传统的HTTP请求-响应模式不同，WebSocket允许服务器主动向客户端推送数据，这对于实时协同编辑场景至关重要。在协同编辑中，用户的每一次按键操作都需要实时同步到其他协作者，如果采用HTTP轮询的方式，将产生大量的冗余请求和网络延迟。WebSocket通过建立持久的双向通信通道，实现了毫秒级的数据传输延迟。

Hocuspocus是一个专为Yjs协同编辑设计的可扩展后端服务器，由Tiptap团队开发和维护。Hocuspocus提供了Yjs协同编辑所需的服务端基础设施，包括WebSocket连接管理、文档状态存储、用户认证和权限控制等功能。Hocuspocus采用钩子（Hook）机制实现可扩展性，开发者可以通过注册自定义钩子函数来干预服务器的各个生命周期阶段。

本系统利用Hocuspocus的以下核心钩子：onAuthenticate钩子用于在用户建立WebSocket连接时验证JWT令牌的有效性；onConnect钩子在用户成功连接后执行，用于记录用户连接信息；onStoreDocument钩子在文档状态变更后被调用，负责将Yjs文档的二进制状态持久化到PostgreSQL数据库，同时触发自动版本快照的创建逻辑；onDisconnect钩子在用户断开连接时执行，用于清理用户状态。

Hocuspocus还支持通过Redis扩展实现多实例部署。在多实例场景下，不同Hocuspocus实例通过Redis的Pub/Sub机制交换Yjs更新数据，确保所有实例上的文档状态保持一致。这种架构设计使得系统能够通过水平扩展来应对更大的并发连接数。

2.6 Tiptap富文本编辑器

Tiptap是一个基于ProseMirror的无头（Headless）富文本编辑器框架。与传统的富文本编辑器（如TinyMCE、CKEditor）不同，Tiptap不提供预定义的UI界面，而是将编辑逻辑与UI表现完全分离，开发者可以根据项目需求自由定制编辑器的外观和交互方式。这种架构设计使得Tiptap具有极高的灵活性和可扩展性，能够适应各种复杂的业务场景和个性化需求。

Tiptap的核心架构完全建立在ProseMirror编辑器引擎之上，继承了ProseMirror强大的文档建模和编辑状态管理能力。ProseMirror提供了一系列核心抽象概念，包括文档模型（Document Model）、编辑状态（Editor State）、事务（Transaction）和插件（Plugin）等。文档模型采用树形结构来表示文档内容，能够自然地表达段落、标题、列表、代码块等多种节点类型及其嵌套关系。编辑状态作为编辑器的"大脑"，封装了当前文档的完整内容和选区信息，所有的编辑操作都必须通过创建事务来修改编辑状态，从而保证了编辑过程的可预测性和一致性。插件系统是ProseMirror最强大的特性之一，它允许开发者以模块化的方式扩展编辑器的功能，无论是添加协作编辑支持、自定义键盘快捷键，还是集成第三方服务，都可以通过插件机制优雅地实现。

在本系统中，我们采用了Tiptap 3版本，并重点利用了@tiptap/extension-collaboration扩展将Tiptap与Yjs进行深度集成。这一扩展是连接编辑器与协同算法的关键桥梁，它通过将编辑器的文档内容映射到Yjs的Y.Text共享类型上，实现了编辑器操作与CRDT数据结构的无缝对接。具体而言，当用户在编辑器中进行输入、删除或格式化操作时，这些操作会被自动转化为Yjs的相应操作并同步到共享文档；反之，当其他协作者对Yjs文档进行修改时，这些变更也会被自动转化为ProseMirror的事务并应用到编辑状态，最终反映在编辑器界面上。这种双向同步机制确保了所有客户端的编辑器状态始终保持一致，为用户提供了流畅的实时协同编辑体验。

为了增强协同编辑的直观感知，我们还集成了@tiptap/extension-collaboration-cursor扩展。该扩展通过实时监听Yjs文档中的光标位置和选区变化，为每个协作者创建可视化的光标标记。每个协作者的光标以不同颜色显示在编辑器中，并带有用户标识信息，使得用户能够清楚地看到其他协作者的实时位置和编辑行为。这种视觉反馈不仅提高了协作效率，还增强了用户的临场感和参与感，特别是在多人同时编辑同一文档的场景下，这种实时可视化功能显得尤为重要。

ProseMirror的文档模型是理解Tiptap工作原理的基础。在ProseMirror中，文档被建模为一个严谨的树形结构，文档由不同类型的节点（Node）组成，每个节点包含内容片段（Fragment）和属性（Attributes）。节点根据其在文档中的作用分为两种基本类型：块级节点（Block Node）和内联节点（Inline Node）。块级节点如段落（Paragraph）、标题（Heading）、代码块（CodeBlock）等，它们代表文档的主要结构单元，通常占据独立的行；内联节点如文本（Text）、粗体标记（Bold Mark）、链接标记（Link Mark）等，它们嵌套在块级节点内部，用于定义文本的格式和语义。这种层次化的文档模型完美地对应了富文本文档的逻辑结构，使得编辑器能够精确地处理各种复杂的编辑场景。

在技术实现层面，ProseMirror的树形文档模型与Yjs的Y.Text数据结构通过Collaboration扩展建立了巧妙的双向映射关系。当编辑器中的操作发生时，操作会被解析并转化为Yjs的插入、删除和格式化操作，这些操作被应用到Yjs的共享数据结构中；同时，Yjs文档的任何远程更新都会被监听器捕获，并转化为ProseMirror的事务（Transaction）应用到编辑状态。这种映射机制确保了编辑器视图与CRDT数据结构之间的实时同步，为协同编辑系统提供了坚实的技术基础。正是通过这种精心设计的架构，Tiptap得以在保持编辑器灵活性的同时，实现了高效、可靠的实时协同编辑功能。

Tiptap的扩展机制基于ProseMirror的插件系统。每个扩展可以定义自己的Schema（声明支持的节点类型和标记类型）、Input Rules（键盘输入规则）、Keyboard Shortcuts（快捷键绑定）和ProseMirror Plugins（底层插件）。本系统使用的Tiptap扩展及其功能如表2-4所示

3 系统需求分析与设计

3.1 系统总体需求

本系统旨在构建一个面向中小型团队的实时协同文档编辑平台，支持多名用户同时对同一份文档进行在线编辑，并能够实时查看其他协作者的编辑内容和光标位置。系统需要提供完整的文档管理功能，包括文档的创建、编辑、组织和归档；提供可靠的版本管理功能，支持历史版本的浏览、对比和回溯；提供安全的用户认证和权限管理功能，确保文档数据的访问安全。

系统的目标用户为需要进行在线协作的团队成员。在典型的使用场景中，团队成员通过注册账号登录系统，在系统中创建和管理文档，邀请其他成员参与文档的协同编辑。在编辑过程中，所有协作者能够实时看到彼此的编辑操作和光标位置，系统自动处理并发编辑产生的冲突。编辑完成后，用户可以手动保存版本快照，也可以利用系统的自动快照功能记录重要的编辑节点。当需要回溯历史修改时，用户可以通过版本时间线浏览历史版本，通过差异对比查看变更内容，并支持将文档回退到指定的历史版本。

系统采用B/S架构，用户通过Web浏览器访问系统，无需安装额外的客户端软件。前端基于Next.js框架构建响应式Web应用，后端基于NestJS框架提供API服务。系统需要支持主流的现代浏览器，包括Google Chrome、Mozilla Firefox、Microsoft Edge和Apple Safari的最新版本。

3.2 功能需求分析

3.2.1 用户管理需求

用户管理模块负责处理用户的注册、登录、会话管理和个人信息维护等功能。具体需求如下：

（1）用户注册功能。用户通过提供邮箱地址、用户名和密码进行注册。系统需要验证邮箱格式的合法性、用户名的唯一性以及密码强度的安全性。注册成功后系统自动创建用户账号并完成登录。

（2）用户登录功能。用户通过邮箱和密码登录系统。登录成功后，服务端通过Set-Cookie响应头设置HttpOnly属性的访问令牌（Access Token）和刷新令牌（Refresh Token），前端仅存储用户基本信息和登录状态标识。后续请求通过浏览器自动携带的Cookie完成身份验证，前端代码不直接接触令牌值，提升了安全性。

（3）令牌刷新机制。当访问令牌过期时，前端自动调用令牌刷新接口获取新的令牌。刷新令牌的有效期为30天，独立存储在专用的Cookie路径下。刷新失败时清除前端登录状态并跳转至登录页面。

（4）个人信息管理。用户登录后可以查看和修改个人资料信息，包括昵称和头像。

（5）安全退出。用户主动退出时，服务端清除数据库中对应的会话记录，前端清除存储的用户信息和登录状态。

3.2.2 文档管理需求

文档管理模块负责文档的创建、组织、搜索和归档等功能。具体需求如下：

（1）文档创建。用户可以在系统中创建新文档，指定文档标题和可选的描述信息。新建文档默认为草稿状态，仅创建者可访问。

（2）文档树形组织。系统支持将文档组织为树形层级结构，用户可以创建子文档或将文档移动到不同的父级下。通过位置（position）字段控制同一层级下的文档排序。

（3）文档列表与搜索。系统提供文档列表页面，支持按”全部文档”“我的文档”“共享文档”“已归档”等分类浏览。提供关键词搜索功能，支持按标题进行模糊匹配。

（4）文档归档与删除。用户可以将不再活跃编辑的文档归档，归档后的文档从主列表中隐藏但可通过归档筛选查看。用户可以删除自己拥有的文档，删除操作为软删除，数据在数据库中保留但标记为已删除状态。

（5）协作权限管理。文档拥有者可以邀请其他用户作为协作者参与文档编辑，并为每个协作者分配角色权限。系统支持三种角色：拥有者（Owner）拥有文档的全部管理权限，包括删除文档和管理协作者；编辑者（Editor）可以编辑文档内容和管理协作者；查看者（Viewer）只能查看文档内容，不能进行编辑操作。

3.2.3 协同编辑需求

协同编辑模块是系统的核心功能模块，负责处理多用户实时协同编辑的技术实现。具体需求如下：

（1）实时编辑同步。多名用户同时编辑同一文档时，所有用户的编辑操作需要实时同步到其他协作者。编辑操作的同步延迟应控制在毫秒级别，确保协作者能够及时看到彼此的修改。

（2）冲突自动解决。当多名用户在文档的相同或相近位置同时进行编辑时，系统需要自动解决冲突，确保所有用户最终看到的文档内容一致。冲突解决过程对用户透明，无需用户手动干预。

（3）协作者感知。用户在编辑文档时能够实时看到其他在线协作者的光标位置和文本选区。每个协作者以不同的颜色标识，方便区分。系统还提供在线用户列表，显示当前正在编辑该文档的所有用户。

（4）只读模式。对于只有查看权限的用户，系统以只读模式展示文档内容，禁止编辑操作，并在界面上明确标识只读状态。

（5）离线编辑支持。当网络暂时中断时，用户的编辑操作在本地继续执行。网络恢复后，本地的编辑操作自动同步到服务器和其他协作者，通过CRDT算法保证一致性。

3.2.4 版本管理需求

版本管理模块负责记录文档的编辑历史，支持版本快照的创建、浏览、对比和回溯。具体需求如下：

（1）自动快照。系统在文档编辑过程中自动创建版本快照，记录文档在特定时间点的完整状态。自动快照按照一定的时间间隔或在关键事件（如用户断开连接）时触发。

（2）手动保存。用户可以在编辑过程中主动创建版本快照，并附加变更说明文字，记录本次保存的原因或主要修改内容。

（3）版本时间线。系统提供版本时间线界面，按时间倒序展示文档的所有历史版本。每个版本记录包含版本号、创建时间、创建者、版本类型（自动保存/手动保存/版本恢复）和变更说明等信息。支持按版本类型进行筛选。

（4）版本差异对比。用户可以查看任意两个版本之间的差异内容，系统以可视化方式展示文本的新增和删除变更，方便用户了解版本间的具体改动。

（5）版本回溯。用户可以将文档回退到指定的历史版本状态。回溯操作会创建一个新的版本快照，类型标记为”版本恢复”，同时保留回溯前的版本记录，确保版本历史的完整性。

3.2.5 用例说明

为从参与者视角对系统行为进行统摄性描述，本系统采用 UML 用例图方法。结合上述功能域划分，确定参与者（Actor）与用例（Use Case）的边界与关系说明如下。

（2）用例包与用例组 用户与账户子域包括：注册、登录、刷新令牌、退出登录、管理个人资料。文档与协作者子域包括：创建文档、浏览与搜索文档、维护文档树与归档、管理协作者与角色。实时协同子域包括：进入文档编辑、实时同步与冲突合并、协作者状态感知、只读访问。版本与历史子域包括：自动版本快照、手动保存版本、浏览版本时间线、版本对比、版本回溯。

（3）用例间关系 「登录」与「刷新令牌」在会话维持场景上存在依赖：访问受保护资源前须具备有效会话。文档拥有者对「管理协作者」的用例与「进入文档编辑」在授权通过上是前置关系；查看者仅关联「以只读方式打开文档」。版本类用例中，「版本回溯」在业务上常依赖于「浏览版本时间线」选择目标版本，可在规约中描述为包含或扩展关系。

3.3 非功能需求分析

3.3.1 性能需求

（1）响应时间。系统的页面加载时间应控制在3秒以内，普通API请求的响应时间应控制在500毫秒以内，协同编辑操作的同步延迟应控制在100毫秒以内。

（2）并发处理能力。系统应能够支持至少50名用户同时在线编辑不同文档，单个文档应能够支持至少10名用户同时协同编辑。

（3）文档容量。系统应支持单篇文档至少10万字符的编辑和存储，文档的打开和保存操作时间不应随文档大小的增加而显著增长。

3.3.2 安全需求

（1）认证安全。系统采用JWT令牌通过HttpOnly Cookie进行认证，令牌不在前端JavaScript代码中暴露。访问令牌的有效期设置为7天，刷新令牌的有效期设置为30天。令牌采用安全的签名算法进行加密。

（2）传输安全。系统在生产环境中强制使用HTTPS协议和WSS（WebSocket Secure）协议进行数据传输，防止数据在传输过程中被窃取或篡改。

（3）输入验证。系统对所有用户输入进行严格的服务端验证，防止SQL注入、跨站脚本攻击（XSS）和跨站请求伪造（CSRF）等常见Web安全威胁。

（4）权限控制。系统实现基于角色的访问控制（RBAC），确保用户只能访问和操作其权限范围内的文档资源。

3.3.3 可用性需求

4.1 概要设计

4.1.1 系统架构设计

本系统采用分层架构设计，整体划分为客户端层、网关层、服务层和数据层四个层次。如图4-1所述，各层之间通过标准化的接口进行通信，实现了关注点分离和松耦合的设计目标。

图4-1 系统分层架构介绍

客户端层是系统的用户交互界面，基于Next.js 15框架构建。客户端层包含三种类型的组件：React服务端组件（Server Components）负责在服务器端渲染静态内容和进行数据预取，减少客户端的JavaScript代码量；React客户端组件（Client Components）负责处理用户交互、状态管理和实时数据同步；Tiptap编辑器组件负责富文本的编辑和渲染，通过Yjs Provider与服务器建立WebSocket连接，实现文档内容的实时同步和协作者感知状态的管理。客户端的状态管理采用Zustand库，结合持久化中间件将用户登录状态等关键数据存储在浏览器的localStorage中。

网关层是系统的实时通信枢纽，由NestJS应用和嵌入式Hocuspocus服务器组成。NestJS应用处理HTTP API请求，包括用户认证、文档管理、版本管理等业务接口。Hocuspocus服务器处理WebSocket连接，负责Yjs文档状态的实时同步和广播。网关层通过生命周期钩子机制介入Hocuspocus的处理流程：在用户连接阶段验证JWT令牌的有效性和文档访问权限；在文档更新阶段接收Yjs的二进制更新数据并广播给同一文档的所有在线用户；在文档持久化阶段将Yjs状态写入数据库并触发版本快照逻辑。

服务层封装了系统的核心业务逻辑，由AuthService、DocumentsService、CollaborationService和VersionsService四个主要服务组成。AuthService负责用户注册、登录验证、JWT令牌生成与刷新、会话管理等认证相关业务。DocumentsService负责文档的增删改查、树形结构管理、协作者管理和权限验证。CollaborationService负责协同编辑过程中的Yjs状态持久化、用户连接管理和自动版本快照创建。VersionsService负责版本快照的创建与管理、版本差异对比和版本回溯操作。

数据层负责数据的持久化存储和缓存管理，由PostgreSQL和Redis两个存储系统组成。PostgreSQL存储用户信息、文档元数据、协作者关系、版本快照和编辑记录等结构化数据，其中Yjs文档状态和版本快照内容以二进制大对象（Bytes）形式存储。Redis用于缓存会话数据、管理分布式锁、存储在线用户感知状态，并通过Pub/Sub机制支持多实例间的状态同步。

4.2.2 认证模块设计

认证模块采用基于JWT的HttpOnly Cookie方案，由认证控制器（AuthController）和认证服务（AuthService）协作完成。认证流程设计如下：

注册流程：用户通过POST /api/auth/register接口提交邮箱、用户名和密码。AuthController接收请求后，调用全局验证管道对请求参数进行格式校验。校验通过后，AuthService使用bcrypt库对密码进行哈希处理（salt rounds设为10），然后将用户信息写入users表。注册成功后自动执行登录流程，生成JWT令牌并通过Cookie返回。

登录流程：用户通过POST /api/auth/login接口提交邮箱和密码。AuthService从数据库中查询对应的用户记录，使用bcrypt的compare方法验证密码。验证通过后，使用jsonwebtoken库签发访问令牌（有效期7天）和刷新令牌（有效期30天），将令牌信息写入sessions表，并通过Set-Cookie响应头将令牌返回给客户端。访问令牌的Cookie属性设置为httpOnly、secure（生产环境）和sameSite=lax；刷新令牌的Cookie路径设置为/api/auth/refresh，限制其仅在令牌刷新请求中被发送。

请求认证流程：NestJS的JWT策略通过自定义提取器优先从Cookie中读取访问令牌，同时兼容Authorization请求头。令牌验证通过后，将用户ID和邮箱信息附加到请求对象上，供后续的守卫和控制器使用。

令牌刷新流程：当前端检测到API请求返回401状态码时，自动调用POST /api/auth/refresh接口。AuthService从Cookie中读取刷新令牌，查询sessions表验证令牌的有效性。验证通过后签发新的访问令牌和刷新令牌，更新sessions表记录，并通过Cookie返回新令牌。前端收到新令牌后自动重试之前失败的请求。

4.2.3 协同编辑模块设计

协同编辑模块基于Yjs和Hocuspocus实现，是系统技术复杂度最高的模块。模块设计围绕数据流和生命周期两个维度展开。

在数据流维度，协同编辑的数据流转过程如下：用户在Tiptap编辑器中执行编辑操作，Tiptap通过Collaboration扩展将操作转化为Yjs的Y.Text变更。Y.Doc将变更编码为二进制更新数据（Update），通过WebSocket连接发送到Hocuspocus服务器。服务器接收到更新数据后，将其广播给同一文档房间内的所有其他在线用户的WebSocket连接。同时，服务器通过防抖机制（延迟2秒，最大间隔10秒）触发onStoreDocument钩子，将Y.Doc的完整二进制状态写入PostgreSQL数据库的documents表content字段。在持久化完成后，服务器调用CollaborationService创建自动版本快照。

在生命周期维度，协同编辑会话经历以下阶段：

连接阶段：客户端通过WebSocket连接到Hocuspocus服务器，携带JWT令牌作为连接参数。服务器的onAuthenticate钩子验证令牌有效性，查询文档协作者关系确认用户有权访问该文档，并根据用户角色设置只读或可编辑模式。

编辑阶段：已连接的用户可以正常编辑文档。服务器接收并转发Yjs更新数据，维护文档的在线用户感知状态（包括光标位置、选区范围和用户信息）。

持久化阶段：文档内容变更时，服务器通过防抖机制定期将文档状态写入数据库。防抖策略为：在首次变更后延迟2秒触发持久化，若持续有变更则每10秒强制执行一次持久化，确保数据不会在内存中停留过长时间。

断开阶段：当用户关闭文档或网络中断时，触发onDisconnect钩子。服务器立即执行最终的文档持久化操作，保存用户离线前的最后编辑状态，并创建一个自动版本快照记录该时刻的文档状态。

4.2.4 版本管理模块设计

版本管理模块负责文档版本快照的全生命周期管理，其设计要点包括版本创建策略、差异对比算法和回溯机制。

版本创建策略：系统支持三种版本创建方式。自动快照由协同编辑模块在用户断开连接或文档持久化时触发创建，type字段标记为AUTO。手动保存由用户在编辑器界面主动触发，用户可以附加变更说明文字，type字段标记为MANUAL。版本回溯产生的快照在用户执行版本回退操作时自动创建，type字段标记为RESTORE。为了避免频繁的自动快照产生过多冗余数据，系统实现了短时间去重机制：在5分钟内的连续自动快照会被覆盖，仅保留最后一次。版本号采用递增整数，每个文档独立编号。

差异对比算法：版本差异对比功能的实现流程为：首先从数据库读取目标版本和前一个版本的Yjs二进制状态快照；将两个二进制状态分别加载到独立的Y.Doc实例中；使用Yjs的DOMBinding或prosemirror-model将Yjs文档转换为HTML或纯文本格式；对两份文本执行差异比较算法（采用Myers差分算法），生成包含新增和删除标记的HTML内容；将差异HTML返回前端进行渲染展示。

回溯机制：版本回溯操作的实现流程为：首先创建当前文档状态的快照（type为RESTORE），记录回溯前的文档状态；然后将目标版本的Yjs二进制状态加载到新的Y.Doc实例中；将Y.Doc的状态编码为完整的更新数据（encodeStateAsUpdate）；将更新数据推送到所有在线用户的WebSocket连接，覆盖当前的文档内容；最后将目标版本的二进制状态写入documents表的content字段完成持久化。

第二，完成了系统的需求分析和总体设计。通过对协同文档编辑场景的深入分析，确定了系统的功能性需求和非功能性需求，设计了基于客户端层、网关层、服务层和数据层的四层系统架构，并完成了功能模块的划分和技术选型。

第三，实现了系统的核心功能模块。用户认证模块采用基于JWT的HttpOnly Cookie方案，保障了认证过程的安全性。协同编辑模块基于Yjs和Hocuspocus构建，实现了毫秒级的实时数据同步和自动冲突解决。版本管理模块支持自动快照、手动保存和版本回溯功能，通过二进制状态存储和差异算法实现了高效的版本对比。文档管理模块支持树形层级组织和基于角色的细粒度权限控制。

本系统仍存在以下不足之处，有待后续改进：

（1）协同编辑的性能优化方面，当前系统在大文档（超过10万字符）场景下的编辑器渲染性能仍有优化空间，后续可以引入虚拟滚动和增量渲染技术进行改进。

（2）版本管理的智能化方面，当前的版本快照策略基于固定的时间间隔，后续可以引入基于内容变更量的自适应快照策略，减少冗余快照的存储开销。

（3）系统的移动端适配方面，当前系统主要针对桌面端浏览器进行了优化，移动端的编辑体验有待进一步提升。

（4）协同感知的丰富化方面，后续可以增加评论、批注、实时聊天等协同功能，提升团队协作的效率。

A Conflict-Free Replicated JSON Datatype

JSON is the de facto standard data interchange format for web and mobile applications. However, the problem of merging concurrent updates to a JSON document by different users has so far been addressed only by ad-hoc approaches. In this paper, we present a formal semantics for JSON, and on that basis define a conflict-free replicated datatype (CRDT) for JSON documents that can be merged deterministically. Our algorithm supports all JSON primitive types, as well as arrays and objects (maps). It handles insertion, update, and deletion of any element, and it ensures that all replicas converge towards the same state. We provide a proof of convergence, and demonstrate the algorithm's performance through an experimental evaluation.

1.INTRODUCTION

JSON (JavaScript Object Notation) has become the de facto standard format for data interchange on the web and in mobile applications. It is used in REST APIs, configuration files, NoSQL databases such as MongoDB and CouchDB, and many other contexts. As collaborative applications become more prevalent, there is an increasing need for multiple users to concurrently edit JSON documents and for those edits to be merged correctly.

For example, consider a web application in which users can edit a shared configuration file in JSON format. If two users concurrently modify different fields of the same JSON object, the system should merge their changes without losing either user's edits. If two users concurrently modify the same field, the system needs a deterministic conflict resolution strategy. Similar requirements arise in collaborative document editing tools, distributed databases with offline operation, and version control systems.

Existing approaches to this problem have significant limitations. Operational Transformation (OT), as used in Google Docs, requires a central server to sequence all operations, creating a single point of failure and a scalability bottleneck. Git and other version control systems require manual conflict resolution. Database replication systems often use last-writer-wins (LWW) semantics, which can silently discard updates. None of these approaches provide a fully satisfactory solution for merging concurrent updates to JSON documents.

Conflict-free replicated data types (CRDTs), as introduced by Shapiro et al., offer a mathematically grounded approach to replication. A CRDT is a data structure that can be replicated across multiple nodes and updated independently, with the guarantee that all replicas will eventually converge to the same state. CRDTs have been defined for several data types, including counters, sets, registers, and sequences. However, no prior work has defined a CRDT for the full JSON data model that supports all of objects, arrays, and primitive values with insertion, update, and deletion operations.

In this paper, we address this gap by presenting a CRDT for JSON documents. Our algorithm allows any number of replicas to be updated independently, and guarantees that all replicas will converge to the same state. The key contributions of this paper are:

We define a formal model of JSON documents as trees with unique identifiers for all nodes, enabling fine-grained tracking of concurrent modifications.

We present algorithms for creating, updating, and deleting any JSON element (objects, arrays, and primitives) in a replicated setting.

We provide a deterministic merge algorithm that resolves all conflicts without requiring user intervention.

We prove that our algorithm ensures convergence: any two replicas that have received the same set of updates will be in the same state.

We experimentally evaluate the performance of our algorithm on documents of various sizes.

Section 5 proves the convergence properties of the algorithm. Section 6 provides an experimental evaluation, and Section 7 concludes.

2.Related Work

Operational Transformation (OT), first described by Ellis and Gibbs, is the most widely used approach for collaborative text editing. OT algorithms transform operations to account for concurrent edits, ensuring that all replicas converge. However, OT requires a central server to establish a total order of operations, making it unsuitable for decentralized or offline-first architectures. Moreover, implementing OT correctly is notoriously difficult, and subtle bugs can lead to divergence.

CRDTs, introduced by Shapiro et al., provide an alternative approach that does not require a central coordinator. CRDTs are classified into state-based (CvRDTs) and operation-based (CmRDTs). Several CRDTs have been defined for specific data types: G-Counters and PN-Counters for integers, G-Sets and OR-Sets for sets, LWW-Registers and MV-Registers for registers, and sequence CRDTs such as Treedoc, Logoot, and RGA for ordered lists. However, these data types operate on flat structures and cannot directly represent the nested, hierarchical nature of JSON documents.

The Automerge library provides a JSON-like CRDT, but its formal specification has not been published as an academic paper. Yjs is a CRDT implementation focused on collaborative text editing using the YATA algorithm, but it does not define a CRDT for general JSON data structures. To our knowledge, our work is the first to formally define a CRDT for the complete JSON data model with support for all JSON types and operations.

3.JSON Tree Model

3.1 Formal Definition

We model a JSON document as a rooted tree. Each node in the tree represents a JSON value. There are three categories of nodes:

Primitive nodes represent JSON primitive values: strings, numbers, booleans, and null.

Object nodes represent JSON objects. Each object node has a set of child nodes, each associated with a unique key (a string).

Array nodes represent JSON arrays. Each array node has an ordered sequence of child nodes.

Every node in the tree is identified by a unique identifier (UID). The UID is a pair (replicaID, sequenceNumber), where replicaID uniquely identifies the replica that created the node, and sequenceNumber is a monotonically increasing counter local to that replica. This ensures that UIDs are globally unique without requiring coordination between replicas.

We formally define a JSON document tree as a tuple D = (V, E, val, type) where:

V is a set of nodes, each identified by a unique UID.

E ⊆ V × V is a set of directed edges from parent to child nodes.

val: V → Value maps primitive nodes to their values.

type: V → {primitive, object, array} maps each node to its type.

For object nodes, each edge from the node to a child is labeled with a key string. For array nodes, the edges are ordered, defining the sequence of elements. This tree model captures the full semantics of JSON while enabling each node to be independently identified and tracked.

3.2 Operations

We define four operations on the JSON tree:

create(parentUID, key, type, value): Creates a new node as a child of the specified parent. For objects, key is the field name; for arrays, key determines the insertion position. The operation generates a new UID for the created node.

update(nodeUID, value): Changes the value of a primitive node identified by its UID.

delete(nodeUID): Removes a node (and its entire subtree) from the tree. The node is marked as deleted (tombstoned) rather than physically removed, ensuring that concurrent create and delete operations can be resolved.

move(nodeUID, newParentUID, key): Moves a node (and its subtree) from its current parent to a new parent at the specified position.

Each operation is tagged with the UID of the replica that performed it and a logical timestamp (a vector clock). This metadata is used by the merge algorithm to determine the causal ordering of operations.

4.CRDT Algorithm

4.1 Object Operations

JSON objects are represented as maps from string keys to child node UIDs. The CRDT algorithm for objects handles concurrent operations as follows:

When two replicas concurrently insert different fields into the same object, both insertions are preserved in the merged state. For example, if replica A inserts "name": "Alice" and replica B concurrently inserts "email": "alice@example.com", the merged object contains both fields. This is because insertions into different keys of an object are independent and commutative.

When two replicas concurrently insert values for the same key, the merge algorithm uses a deterministic conflict resolution rule based on the UIDs of the inserted values. The value with the lexicographically greater UID is retained, and the other is discarded. This ensures that all replicas make the same choice, guaranteeing convergence.

When one replica updates a field while another replica deletes it, the delete operation takes precedence. The field is removed from the merged state. This policy ensures that explicit deletion is respected, even if other replicas have pending updates.

4.2 Array Operations

Arrays are the most complex part of the JSON CRDT due to the need to maintain ordering of elements. Each array element has a UID and a position within the array. The position is not represented as a simple integer index (which would be ambiguous under concurrent modifications), but rather as a fractional index or a list of UIDs that define the element's order relative to its neighbors.

When a replica inserts a new element into an array, it specifies the UIDs of the elements immediately before and after the insertion point. This interleaving approach ensures that the insertion position is unambiguous, even when other replicas concurrently insert elements at nearby positions. For example, if the array contains elements [A, B] and a replica inserts X between A and B, the position of X is recorded as "between A and B". If another replica concurrently inserts Y between A and B, the positions of X and Y are both "between A and B", and they are ordered by their UIDs.

Delete operations mark elements as tombstoned rather than removing them from the array structure. Tombstones are hidden from the application-level view of the array but retained in the CRDT state to ensure that concurrent operations can be correctly resolved. A garbage collection mechanism can safely remove tombstones once all replicas have acknowledged the deletion.

Move operations change the position of an element within an array. A move is processed as a combination of a deletion at the old position and an insertion at the new position. The merge algorithm handles concurrent moves by applying them in causal order and resolving conflicts using the UID-based deterministic rule.

4.3 Primitive Value Operations

Primitive values (strings, numbers, booleans, null) use a last-writer-wins (LWW) register CRDT. Each update to a primitive value is tagged with a logical timestamp from the updating replica. When merging concurrent updates to the same value, the update with the greater logical timestamp wins. If the timestamps are equal (which can happen if two replicas update the value simultaneously with the same logical clock value), the UID of the updating replica is used as a tiebreaker, ensuring deterministic resolution.

4.4 Merge Algorithm

The merge algorithm takes two document trees and produces a merged tree that incorporates all changes from both inputs. The algorithm proceeds recursively from the root:

For each node, collect the set of operations that have been applied to it in both trees.

Determine the causal ordering of operations using vector clocks.

Apply operations in causal order. Concurrent operations (those that are not causally related) are resolved using the deterministic rules described above.

Recursively merge the children of object and array nodes.

The merge function is commutative, associative, and idempotent, ensuring that it satisfies the requirements of a state-based CRDT. These properties guarantee that all replicas converge to the same state regardless of the order in which they receive updates.

5.Convergence Proof

We sketch the proof of convergence. The full proof is provided in the appendix of the paper.

Theorem: Any two replicas that have received the same set of operations (in any order) will converge to the same state.

Proof sketch: We show that the merge function satisfies three properties:

Commutativity: merge(A, B) = merge(B, A) for any two document trees A and B. This follows from the fact that the merge algorithm resolves concurrent operations using deterministic rules (UID-based ordering and LWW timestamps) that do not depend on the order of the input trees.

Associativity: merge(merge(A, B), C) = merge(A, merge(B, C)) for any three document trees A, B, and C. This follows from the commutativity and idempotence of the per-node merge operations.

Idempotence: merge(A, A) = A for any document tree A. This follows because merging a document with itself results in applying the same set of operations twice, and all operations are idempotent (tombstones remain tombstoned, values remain the same).

Since the merge function satisfies these three properties, the state space of JSON documents forms a join semi-lattice. By the properties of semi-lattices, repeatedly applying the merge function to any set of replicas that have received the same operations will converge to the unique least upper bound of all states, which is the same for all replicas.

6.Experimental Evaluation

We implemented the JSON CRDT algorithm in JavaScript and evaluated its performance on documents of varying sizes. All experiments were run on a machine with an Intel Core i7 processor and 16 GB of RAM.

6.1 Merge Performance

We measured the time to merge two document trees of various sizes. The results show that merge time grows linearly with the number of nodes in the document. For a document with 1,000 nodes, the merge completes in approximately 2 milliseconds. For 10,000 nodes, the merge takes approximately 15 milliseconds. For 100,000 nodes, the merge takes approximately 180 milliseconds.

These results demonstrate that the algorithm is practical for documents of moderate size. The linear scaling is expected because the merge algorithm processes each node exactly once.

6.2 Memory Overhead

We measured the memory overhead of the CRDT metadata (UIDs, tombstones, vector clocks) compared to a plain JSON document. The overhead is approximately 2-3x the size of the original JSON document. This overhead is primarily due to the storage of UIDs for each node and the retention of tombstones for deleted elements. A garbage collection process can reduce this overhead by removing tombstones that are no longer needed for conflict resolution.

7.Conclusion

We have presented a conflict-free replicated datatype (CRDT) for JSON documents that supports all JSON types and operations. Our algorithm enables multiple replicas to be updated independently and guarantees convergence to the same state. We have provided a formal model, a deterministic merge algorithm, a proof of convergence, and an experimental evaluation. The results demonstrate that JSON CRDT is practical for real-world applications, with merge operations completing in milliseconds for documents of moderate size.

This work opens several directions for future research. First, the memory overhead of CRDT metadata could be reduced through more compact encoding schemes. Second, the garbage collection of tombstones could be made more efficient. Third, the algorithm could be extended to support richer data types such as binary data, timestamps, and geometric types. Finally, integration with existing collaborative editing frameworks such as Yjs and Automerge would enable practical deployment in web applications.

一种无冲突复制JSON数据类型

JSON已成为Web和移动应用程序数据交换的事实标准格式。然而，迄今为止，针对不同用户对JSON文档的并发更新进行合并这一问题，仅采用了临时性的方案。本文定义了JSON的形式化语义，并在此基础上提出了一种可以确定性合并的JSON文档无冲突复制数据类型（CRDT）。该算法支持所有JSON原始类型，以及数组与对象（映射）。它能够处理任意元素的插入、更新和删除操作，并确保所有副本收敛到相同的状态。本文给出了收敛性证明，并通过实验评估验证了算法的性能。

1.引言

JSON（JavaScript 对象表示法）已成为Web和移动应用中数据交换的事实标准格式。它被广泛应用于REST API、配置文件、MongoDB和CouchDB等NoSQL数据库以及众多其他场景。随着协作应用的日益普及，越来越多的场景需要多名用户同时编辑 JSON 文档并正确合并各自的编辑内容。

例如，考虑一个Web应用，用户可以在其中以JSON格式编辑共享配置文件。如果两名用户同时修改同一JSON对象的不同字段，系统应当合并他们的变更而不丢失任何一方的编辑。如果两名用户同时修改同一字段，系统则需要一种确定性的冲突解决策略。类似的需求也出现在协作文档编辑工具、支持离线操作的分布式数据库以及版本控制系统中。

现有的解决方案存在显著局限。操作转换（OT）算法（如Google Docs所采用的）需要一台中央服务器对所有操作进行排序，这造成了单点故障和可扩展性瓶颈。Git等版本控制系统需要手动解决冲突。数据库复制系统通常采用最后写入者胜出（LWW）语义，可能静默丢弃更新。这些方法均不能为JSON文档的并发更新合并提供完全令人满意的解决方案。

Shapiro等人提出的无冲突复制数据类型（CRDT）为复制问题提供了一种基于数学理论的方法。CRDT是一种可以在多个节点上复制并独立更新的数据结构，保证所有副本最终收敛到相同的状态。目前已为多种数据类型定义了CRDT，包括计数器、集合、寄存器和序列。然而，此前尚无工作为完整的JSON数据模型定义支持对象、数组和原始类型全部插入、更新和删除操作的CRDT。

本文填补了这一空白，提出了一种面向JSON文档的CRDT。该算法允许任意数量的副本独立更新，并保证所有副本收敛到相同的状态。本文的主要贡献如下：

定义了JSON文档的树形形式化模型，为所有节点分配唯一标识符，从而实现细粒度的并发修改追踪。

提出了在复制环境中创建、更新和删除任意JSON元素（对象、数组和原始类型）的算法。

设计了无需用户介入即可解决所有冲突的确定性合并算法。

证明了该算法保证收敛性：接收到相同更新集合的任意两个副本将处于相同状态。

通过实验评估了算法在不同规模文档上的性能。

本文剩余部分结构如下：第2节讨论相关工作；第3节定义JSON树形模型及其形式化语义；第4节给出面向JSON的CRDT算法；第5节证明算法的收敛性质；第6节提供实验评估；第7节进行总结。

2 相关工作

操作转换（OT）由Ellis和Gibbs首次提出，是目前协同文本编辑领域使用最广泛的方法。OT算法通过转换操作来处理并发编辑，确保所有副本收敛。然而，OT需要一台中央服务器来确定操作的全序，使其不适用于去中心化或离线优先的架构。此外，正确实现OT出了名地困难，细微的缺陷就可能导致副本发散。

Shapiro等人引入的CRDT提供了一种不需要中央协调器的替代方案。CRDT分为基于状态的（CvRDT）和基于操作的（CmRDT）两类。目前已为多种特定数据类型定义了CRDT：用于整数的G-Counter和PN-Counter，用于集合的G-Set和OR-Set，用于寄存器的LWW-Register和MV-Register，以及用于有序列表的序列CRDT（如Treedoc、Logoot和RGA）。然而，这些数据类型作用于扁平结构，无法直接表示JSON文档的嵌套层次特性。

Automerge库提供了类似JSON的CRDT，但其形式化规范尚未以学术论文形式发表。Yjs是一个基于YATA算法的协同文本编辑CRDT实现，但它并未定义面向通用JSON数据结构的CRDT。据我们所知，本文的工作是首次为完整的JSON数据模型形式化定义支持所有JSON类型和操作的CRDT。

3 JSON树形模型

3.1 形式化定义

我们将JSON文档建模为一棵有根树。树中的每个节点表示一个JSON值。节点分为三类：

原始节点表示JSON原始值：字符串、数字、布尔值和null。

对象节点表示JSON对象。每个对象节点拥有一组子节点，每个子节点关联一个唯一的键（字符串）。

数组节点表示JSON数组。每个数组节点拥有一个有序的子节点序列。

树中的每个节点由一个唯一标识符（UID）标识。UID是一个二元组(replicaID, sequenceNumber)，其中replicaID唯一标识创建该节点的副本，sequenceNumber是该副本本地单调递增的计数器。这确保了UID全局唯一，无需副本之间的协调。

我们将JSON文档树形式化定义为元组D = (V, E, val, type)，其中：

V是节点集合，每个节点由唯一UID标识。

E⊆V×V是从父节点到子节点的有向边集合。

val:V→ Value将原始节点映射到其值。

type: V→{primitive, object, array}将每个节点映射到其类型。

对于对象节点，从该节点到子节点的每条边标记有一个键字符串。对于数组节点，边是有序的，定义了元素的序列。该树模型捕获了JSON的完整语义，同时使每个节点能够被独立标识和追踪。

3.2 操作

我们在JSON树上定义四种操作：

create(parentUID, key, type, value)：创建一个新节点作为指定父节点的子节点。对于对象，key是字段名；对于数组，key决定插入位置。该操作为新创建的节点生成一个UID。

update(nodeUID, value)：修改由UID标识的原始节点的值。

delete(nodeUID)：从树中移除一个节点（及其整个子树）。该节点被标记为已删除（墓碑化）而非物理移除，以确保并发的创建和删除操作可以被正确解决。

move(nodeUID, newParentUID, key)：将一个节点（及其子树）从当前父节点移动到新父节点的指定位置。

每个操作都标记了执行该操作的副本UID和逻辑时间戳（向量时钟）。这些元数据被合并算法用于确定操作的因果序。

4.CRDT算法

4.1 对象操作

JSON对象被表示为从字符串键到子节点UID的映射。对象的CRDT算法按如下方式处理并发操作：

当两个副本同时向同一对象插入不同字段时，两次插入都在合并后的状态中保留。例如，如果副本A插入"name": "Alice"，副本B同时插入"email": "alice@example.com"，则合并后的对象包含两个字段。这是因为插入到对象的不同键是相互独立且满足交换律的。

当两个副本同时向同一键插入值时，合并算法基于所插入值的UID的确定性冲突解决规则进行判断。字典序较大的UID对应的值被保留，另一个被丢弃。这确保了所有副本做出相同的选择，保证了收敛性。

当一个副本更新某字段而另一个副本删除该字段时，删除操作优先。该字段从合并状态中移除。该策略确保显式删除操作受到尊重，即使其他副本有待处理的更新。

4.2 数组操作

数组是JSON CRDT中最复杂的部分，因为需要维护元素的顺序。每个数组元素拥有一个UID和在数组中的位置。该位置不表示为简单的整数索引（在并发修改下会产生歧义），而是表示为分数索引或定义元素相对于相邻元素顺序的UID列表。

当副本向数组插入新元素时，它指定紧邻插入点前后元素的UID。这种交错方式确保插入位置无歧义，即使其他副本同时在附近位置插入元素。例如，如果数组包含元素[A, B]，一个副本在A和B之间插入X，则X的位置记录为"在A和B之间"。如果另一个副本同时在A和B之间插入Y，则X和Y的位置都是"在A和B之间"，它们按UID排序。

删除操作将元素标记为墓碑而非从数组结构中物理移除。墓碑在应用层视图上被隐藏，但保留在CRDT状态中，以确保并发操作可以被正确解决。垃圾回收机制可以在所有副本确认删除后安全地移除墓碑。

移动操作改变元素在数组中的位置。移动被处理为在旧位置的删除和在新位置的插入的组合。合并算法按因果序处理并发移动，并使用基于UID的确定性规则解决冲突。

4.3 原始值操作

原始值（字符串、数字、布尔值、null）使用最后写入者胜出（LWW）寄存器CRDT。对原始值的每次更新都标记有来自更新副本的逻辑时间戳。合并对同一值的并发更新时，逻辑时间戳较大的更新胜出。如果时间戳相等（两个副本以相同逻辑时钟值同时更新时可能发生），则使用更新副本的UID作为决胜规则，确保确定性的解决。

4.4 合并算法

合并算法接收两棵文档树，产生一棵融合了两棵输入所有变更的合并树。算法从根节点开始递归执行：

对于每个节点，收集在两棵树中已应用于该节点的操作集合。

使用向量时钟确定操作的因果序。

按因果序应用操作。并发操作（无因果关系的）使用前述确定性规则解决。

递归合并对象和数组节点的子节点。

合并函数满足交换律、结合律和幂等性，确保其满足基于状态的CRDT的要求。这些性质保证了所有副本无论以何种顺序接收更新，都将收敛到相同的状态。

收敛性证明

以下给出收敛性证明的概要。完整证明见论文附录。

定理：接收到相同操作集合（以任意顺序）的任意两个副本将收敛到相同的状态。

证明概要：我们证明合并函数满足三个性质：

交换律：对于任意两棵文档树A和B，merge(A, B) = merge(B, A)。这源于合并算法使用确定性规则（基于UID的排序和LWW时间戳）解决并发操作，这些规则不依赖于输入树的顺序。

结合律：对于任意三棵文档树A、B和C，merge(merge(A, B), C) = merge(A, merge(B, C))。这源于逐节点合并操作的交换律和幂等性。

幂等性：对于任意文档树A，merge(A, A)=A。这源于将文档与自身合并等价于两次应用相同的操作集，而所有操作满足幂等性（墓碑保持墓碑状态，值保持不变）。

由于合并函数满足上述三个性质，JSON文档的状态空间构成一个并半格。根据半格的性质，对接收到相同操作集合的任意副本集合反复应用合并函数，将收敛到所有状态的唯一最小上界，即所有副本收敛到相同状态。

5.实验评估

我们使用JavaScript实现了JSON CRDT算法，并在不同规模的文档上评估了其性能。所有实验在一台配备Intel Core i7处理器和16 GB内存的机器上运行。

6.1 合并性能

我们测量了合并不同规模文档树所需的时间。结果表明，合并时间与文档节点数呈线性增长。对于包含1,000个节点的文档，合并在约2毫秒内完成。对于10,000个节点，合并耗时约15毫秒。对于100,000个节点，合并耗时约180毫秒。

这些结果表明该算法对于中等规模的文档是实用的。线性增长是预期的，因为合并算法对每个节点恰好处理一次。

6.2 内存开销

我们测量了CRDT元数据（UID、墓碑、向量时钟）相对于普通JSON文档的内存开销。开销约为原始JSON文档大小的2-3倍。这些开销主要源于为每个节点存储UID以及保留已删除元素的墓碑。垃圾回收过程可以通过移除不再需要用于冲突解决的墓碑来降低此开销。

结论

本文提出了一种支持所有JSON类型和操作的无冲突复制数据类型（CRDT）。该算法允许多个副本独立更新，并保证收敛到相同的状态。我们提供了形式化模型、确定性合并算法、收敛性证明和实验评估。结果表明，JSON CRDT对于实际应用是可行的，中等规模文档的合并操作可在毫秒级别完成。

该工作开辟了多个未来研究方向。首先，可以通过更紧凑的编码方案降低CRDT元数据的内存开销。其次，可以提高墓碑垃圾回收的效率。第三，可以将算法扩展以支持更丰富的数据类型，如二进制数据、时间戳和几何类型。最后，与Yjs和Automerge等现有协同编辑框架的集成将使其能够在Web应用中实际部署。
